Background

If you're new here: this page explains a change to an agent extension — a small program that adds a slash command to an AI coding agent. A command works like a CLI tool: you type /explain-diff-html, the extension's handler runs, and it ends by handing the agent a task. This particular command turns a git change into a self-contained HTML page — Background, Intuition, Code, and Quiz sections — exactly like the page you are reading now.

What the command did before

The extension is small: one handler in src/index.ts, a workflow document in skills/explain-diff-html/SKILL.md, a packaged HTML template, and a validator script. The handler took one optional argument and silently defaulted everything else:

const target = args.trim() || "uncommitted working-tree changes";

No argument meant exactly one thing: uncommitted working-tree changes. To explain a PR you had to already know the syntax /explain-diff-html #123; a commit range was /explain-diff-html a..b; a branch was just its name. The command also committed to its action immediately — it created the output directory, copied the template into a dated file, and only then launched the explanation task with a Target: line telling the agent which git commands to run.

How a target becomes an explanation

Every generated file lands in ~/.omp/explain-diffs/ as YYYY-MM-DD-explanation-<slug>.html. The slug is produced by a small slugify function: lowercase, runs of non-alphanumerics become dashes, a leading # becomes pr-, capped at 60 characters. The Target: value is resolved by rules in the skill — #N means gh pr diff N, a branch means git diff <default-branch>...<branch>, a range means git diff <range>, anything else means git diff <arg> — and the same rule drives the header diffstat (shortstat/numstat) on the page.

The interactive side of the harness

Extensions run inside the agent harness, which exposes UI helpers through ctx.ui:

  • select(label, options) — a menu; resolves to the chosen option, or undefined if the user escapes or it times out.
  • input(label, placeholder?) — a text field; resolves to the typed string, or undefined on cancel.
  • notify(message, level) — a one-line status message.

This PR is the first time the command uses that interactive API: select and input to gather a target, notify to report cancellation.

Key idea A target is a description of a code change — uncommitted working tree, a PR, a commit, a range — that the skill turns into concrete git commands. This change adds a way to choose a target interactively instead of being locked into one default.

Intuition

The old command had two rough edges. The default was silent and surprising: a bare /explain-diff-html explained the working tree, whether or not that was what you wanted. And there was no "change my mind": the moment the command ran, it created a directory and a file.

The fix reframes the command as a pipeline with a decision gate at the front. Deciding what to explain — pure conversation, no side effects — is separated from creating the page — filesystem writes. If you cancel at the gate, nothing has happened yet.

bare /explain-diff-html
▼
resolveTarget(args, ctx.ui)
▼
menu → per-kind input → { label, slug }
▼
mkdir → copy template → task prompt with Target: label
Escaping at any prompt returns null → notify "cancelled — nothing created" → early return, filesystem untouched.

The gate has two lanes. An explicit argument sails straight through — the fast path, byte-for-byte the old behavior. Only a bare invocation stops at the menu:

args.trim() non-empty?
▼ yes — fast path
{ label: args, slug: args } — menu never shown
▼ no — interactive
5-option menu → SHA / PR # / base / free text → { label, slug }
Either lane ends in the same shape: a label for the agent, a slug for the filename.

Every resolved target is a pair, and the two halves serve different consumers:

Choosing "A specific commit" and entering a1b2c3d4e5f67890 yields label commit a1b2c3d4e5f67890 but slug a1b2c3d4e5f6 (first 12 characters). Same idea, two formats, two consumers.

Why order matters Cancelling is free because resolution happens strictly before creation. In the old code the very first statements were mkdirSync and the template copy; in the new code those run only after resolveTarget has returned a real target. Escaping a prompt is therefore a no-op on disk — not a cleanup, just a decision that was never made.

Code

The diff touches three files, but the substance is in src/index.ts: a new resolveTarget helper plus two small types. The skill and README changes extend the target language the workflow understands.

1. Resolution before side effects

The handler's first act is now a question, not a write. Before this PR the first statements created the output directory and copied the template; now resolveTarget runs first, and a null result (cancel) returns immediately:

const target = await resolveTarget(args, ctx.ui);
if (!target) return;

const outDir =
  process.env.EXPLAIN_DIFF_OUTPUT_DIR ??
  join(homedir(), ".omp", "explain-diffs");
mkdirSync(outDir, { recursive: true });

This ordering is the whole point: resolveTarget only talks to the user — no files, no network. Every filesystem operation happens strictly after the decision.

2. The contract: label vs slug

Two types define the shape of a resolved target and the UI surface the helper needs:

type ResolvedTarget = { label: string; slug: string } | null;

type TargetUi = {
  select(label: string, options: string[]): Promise<string | undefined>;
  input(label: string, placeholder?: string): Promise<string | undefined>;
  notify(message: string, level: "info" | "error"): void;
};

TargetUi is a minimal structural type for ctx.ui — the handler passes the real object, and the type keeps resolveTarget self-contained (and easy to test in isolation, as the PR's smoke test does).

3. Fast path: explicit arguments unchanged

Anything non-empty trims and passes straight through, exactly as before:

const trimmed = args.trim();
if (trimmed) return { label: trimmed, slug: trimmed };

So /explain-diff-html #7 never shows the menu: the target is #7, and slugify's leading-# rule turns it into pr-7.

4. The menu and the cancel helper

A bare invocation shows five options. Escaping returns undefined, which routes to cancel() — a notify plus null:

const cancel = (): null => {
  ui.notify("explain-diff-html: cancelled — nothing created", "info");
  return null;
};

const choice = await ui.select("What do you want explained?", [
  "Uncommitted changes",
  "A specific commit",
  "A specific PR (GitHub PR #)",
  "A specific commit vs a base revision",
  "Other (type your own)",
]);
if (!choice) return cancel();

5. Per-kind gathering

Each menu option collects exactly what its git rule needs, then builds its label/slug pair. Empty input at any point is treated as a cancel:

switch (choice) {
  case "Uncommitted changes":
    return { label: "uncommitted working-tree changes", slug: "uncommitted" };
  case "A specific commit": {
    const sha = (await ui.input("Commit (SHA or ref):", "e.g. a1b2c3d") ?? "").trim();
    if (!sha) return cancel();
    return { label: `commit ${sha}`, slug: sha.slice(0, 12) };
  }
  case "A specific PR (GitHub PR #)": {
    const n = (await ui.input("GitHub PR number:", "e.g. 123") ?? "").trim();
    if (!n) return cancel();
    return { label: `#${n}`, slug: `pr-${n}` };
  }
  // "commit vs base" reads two inputs and returns
  //   { label: `${sha} vs ${base}`, slug: `${sha.slice(0, 12)} vs ${base}` }
  // "Other" returns { label: text, slug: text } for the typed free text.
}

The "commit vs base" slug still flows through slugify, so a1b2c3d4e5f6 vs main becomes the filename a1b2c3d4e5f6-vs-main.

6. Wiring label and slug into the pipeline

const slug = slugify(target.slug);
const outPath = join(outDir, `${date}-explanation-${slug}.html`);
// …
Target: ${target.label}

The label lands in the Target: line the agent sees; the slug lands in the filename. Previously both came from the raw argument — now they may differ (e.g. commit a1b2c3d4e5f67890 vs a1b2c3d4e5f6).

7. The skill learns the new targets

SKILL.md now matches its rules against the Target: line and adds two rules for the menu's commit-based options:

  • commit <sha> — git diff <sha>^ <sha>, with a root-commit fallback: if the parent lookup fails, diff against the empty tree so the whole commit still renders as additions.
  • <commit> vs <base> — git diff <base>...<commit>, i.e. merge-base (PR) semantics without needing GitHub.

Both kinds also get matching shortstat/numstat commands so the header diffstat works for them. Direct skill invocation with no target asks the same menu through the ask tool instead of silently defaulting, and the README's usage table advertises the interactive bare invocation.

Edge case git diff <sha>^ <sha> fails when the commit has no parent. The skill checks git rev-parse --verify --quiet <sha>^; a non-zero exit means root commit, and it falls back to diffing against the empty tree — the entire commit appears as one additions block.

Quiz

1. A user runs the bare command, picks "A specific commit", and enters a1b2c3d4e5f67890. What pair does the command produce?

The commit branch returns { label: \`commit ${sha}\`, slug: sha.slice(0, 12) }: the prompt gets the full commit a1b2c3d4e5f67890 label while the filename uses the first 12 characters. The second option drops the "commit" prefix the skill's rule needs; the third keeps the full SHA and adds a "commit-" prefix that doesn't exist; the fourth is the PR format (#N → pr-N).

2. Why does resolveTarget run before mkdirSync in the handler?

Resolution is pure conversation; if (!target) return; stops before the first filesystem call, so an escape at any prompt is a no-op on disk. No such directory-vs-target validation exists — outDir comes from env or home only. The date is independent of the target. And mkdirSync only needs outDir; the slug affects the filename, not the directory.

3. Which path produces the file 2026-08-14-explanation-pr-42.html?

The PR branch returns slug pr-42, which slugify keeps as-is. "A specific commit" gives slug 42 (label commit 42); "Other" gives label and slug both 42; and an explicit argument takes the fast path with no menu, so the target is the literal 42 — the pr- prefix only comes from a leading #.

4. What happens when an explicit argument like #7 is passed?

if (trimmed) return { label: trimmed, slug: trimmed }; short-circuits before any UI, and slugify's leading-# rule produces pr-7. The menu exists only for the bare invocation. The argument comes from the harness, not a shell. And the silent uncommitted default is exactly the behavior this PR removes.

5. The skill adds a commit <sha> rule. What happens when that commit is the root commit (no parent)?

git rev-parse --verify --quiet <sha>^ exits non-zero for a root commit, so the rule diffs against the empty tree — the commit's full content is still explained. The fallback exists precisely to avoid an error. The default branch is the branch rule with different semantics, and uncommitted changes is unrelated to commit targets.
